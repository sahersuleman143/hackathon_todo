# Implementation Plan: Full-Stack Todo Web Application (Phase II)

**Branch**: `002-fullstack-todo-webapp` | **Date**: 2026-01-30 | **Spec**: [spec.md](./spec.md)
**Input**: Fullstack multi-user todo web app with authentication and persistent storage

## Summary

Evolution from Phase I console app to full-stack web application with multi-user authentication, persistent PostgreSQL storage via Neon, and modern web UI. Backend built with FastAPI + SQLModel provides RESTful CRUD API with JWT authentication via Better Auth. Frontend uses Next.js 16+ App Router with TypeScript and Tailwind CSS for responsive, authenticated task management. All user data is strictly isolated - users can only access their own tasks.

## Technical Context

**Languages/Versions**: Python 3.11+, Node.js 18+, TypeScript 5.3+, Next.js 16.8+
**Backend Stack**: FastAPI 0.104+, SQLModel 0.14+, Python-JOSE, python-multipart
**Frontend Stack**: Next.js 16.8+ (App Router), React 18, TypeScript, Tailwind CSS 3.4+
**Authentication**: Better Auth (JWT tokens, shared secret), HTTPOnly cookies
**Database**: Neon Serverless PostgreSQL 15+ with DATABASE_URL from .env

**Performance Goals**: Dashboard load <2s, task operations <3s, 100 concurrent users
**Constraints**: Password hashing required (bcrypt), all inputs validated, user isolation enforced
**Scale**: Multi-tenant architecture, up to 10k users, tasks per user unlimited

## Architecture Deep Dive

### Backend Architecture

**FastAPI Application Structure**:
- `main.py` creates FastAPI app with CORS and router inclusion
- Prefix all API routes with `/api` for reverse proxy compatibility
- Middleware: Structured logging, error handlers (400/401/404/500), security headers
- Lifespan context manager for database connectivity and cleanup

**Authentication & Authorization**:
- JWT tokens issued on successful login/registrations
- HTTPOnly cookies for token storage (XSS protection)
- `get_current_user` dependency extracts user from JWT and validates against database
- All `/api` endpoints (except auth) require authentication
- Password hashing: bcrypt with cost factor 12

**Database Layer**:
- `SQLModel` models inherit from both SQLAlchemy and Pydantic
- Single `DATABASE_URL` from `.env` configures Neon PostgreSQL connection
- Engine created with `sqlmodel.create_engine(DATABASE_URL)`
- Session dependency provides per-request database session with automatic cleanup
- Foreign key relationships: User (one) → Task (many)

**API Routes**:
- `/api/auth/register` (POST): Creates user, validates unique email, hashes password, returns JWT
- `/api/auth/login` (POST): Validates credentials, returns JWT on success, 401 on failure
- `/api/auth/logout` (POST): Client clears token (stateless JWT - no server-side invalidation)
- `/api/tasks` (GET): Returns all tasks for current user, sorted by created_at desc
- `/api/tasks` (POST): Creates new task with current user_id, validates title/description
- `/api/tasks/{id}` (GET): Returns specific task if owned by current user, else 404
- `/api/tasks/{id}` (PUT): Updates title/description, validates, returns updated task
- `/api/tasks/{id}` (PATCH): Toggles completed status, returns updated task
- `/api/tasks/{id}` (DELETE): Soft or hard delete (decision in implementation)

**Security Principles**:
- User isolation enforced at database query level (`WHERE user_id = current_user.id`)
- No endpoint returns data without user_id filter
- 404 returned for unauthorized tasks (not 403 - don't reveal existence)
- All inputs validated using Pydantic/SQLModel field constraints
- SQL injection prevention via SQLModel/SQLAlchemy parameter binding
- CORS configured for frontend origin only (Vercel production, localhost dev)

**Error Handling**:
- 400: Validation errors (title required, email format, length limits)
- 401: Missing/invalid/expired JWT, "Unauthorized" message
- 404: Resource not found or not owned by user
- 409: Email already registered
- 500: Internal server errors (database connection, unexpected failures)
- All errors return JSON with descriptive messages, never stack traces

**Service Layer**:
- `task_service.py` encapsulates business logic: create, read, update, delete, toggle
- `user_service.py` handles registration with duplicate email checking, password hashing
- Services accept database session and return SQLModel instances
- Services raise domain-specific exceptions mapped to HTTP status codes

### Frontend Architecture

**Next.js App Router Structure**:
- Root layout wraps entire app with Better Auth provider
- `/` page: Redirects to login if unauthenticated, to dashboard if authenticated
- `/login` page: Login form, redirects to dashboard on success
- `/dashboard` page: Protected route, shows task list + create form
- Server components for initial data fetch, client components for interactivity

**Authentication Flow**:
1. User submits credentials → Frontend API call to `/api/auth/login`
2. Backend validates → Returns JWT token
3. Frontend stores token in HTTPOnly cookie via Better Auth
4. Subsequent requests automatically include JWT in Authorization header
5. `get_current_user` dependency extracts and validates token
6. Frontend checks auth state via `useAuth` hook (checks cookie/local state)
7. Protected routes redirect to login if unauthenticated

**Better Auth Integration**:
- Configuration in `lib/auth/config.ts` - JWT secret, token expiry (7 days)
- `useAuth` hook provides: user, login, logout, isLoading, isAuthenticated
- Login/logout actions clear/populate cookies and redirect appropriately
- Client-side auth guard components for protected sections

**API Client Layer**:
- `lib/api/client.ts` provides `fetch` wrapper for consistency
- Automatic JWT inclusion from cookies
- JSON serialization, error handling, response parsing
- AbortController support for request cancellation
- Specific modules: `auth.ts`, `tasks.ts` for endpoint-specific logic

**Component Architecture**:
- `TaskList`: Fetches tasks on mount, passes tasks to `TaskItem` components
- `TaskItem`: Displays task info, handles edit/delete/complete actions
- `CreateTaskForm`: Modal or inline form, validates title, calls create API
- `EditTaskForm`: Inline edit or separate route with form pre-population
- `LoginForm`: Email/password validation, error display, loading states
- All forms: loading states, error messages, success feedback, disabled on submit

**State Management**:
- Server-side initial data fetch where possible (Next.js SSR)
- Client-side state for: auth status, form inputs, loading states, errors
- No global state management library needed (React state + SWR/React Query optional)
- Optimistic UI updates for task toggles and edits (immediate feedback, revert on error)

**Routing**:
- Public routes: `/login`, `/` (landing/redirect)
- Protected routes: `/dashboard` and all its children
- `/dashboard/tasks/[id]` optional for task detail view (future enhancement)
- Redirect unauthenticated users to `/login`
- Redirect authenticated users away from `/login` to `/dashboard`

**UI/UX Considerations**:
- Tailwind CSS for consistent styling with utility classes
- Responsive design: mobile-first approach, works 320px+
- Task status: checkboxes/checkmarks with visual distinction
- Long descriptions: truncated in list view, full in edit/detail view
- Loading states: skeletons or spinners during API calls
- Error messages: contextual, near form inputs or as toast notifications
- Success feedback: subtle but clear (checkmark animation, brief message)

**Form Validation**:
- Client-side validation mirrors backend validation
- Required title field: min length 1, max length 200
- Optional description: max length 1000
- Email validation: regex pattern matching
- Password: minimum 8 characters
- Real-time feedback where appropriate, full validation on blur/submit

### Database Schema

**Tables & Columns**:

```sql
-- Users table
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Tasks table
CREATE TABLE tasks (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(200) NOT NULL,
    description TEXT,
    completed BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_tasks_user_id (user_id)
);

-- Optional: Index for faster user task queries
CREATE INDEX idx_tasks_user_id_created_at ON tasks(user_id, created_at DESC);
```

**SQLModel Implementation**:
```python
# Backend models/user.py
class User(SQLModel, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    email: str = Field(max_length=255, unique=True, index=True)
    password_hash: str
    created_at: datetime = Field(default_factory=datetime.utcnow)

# Backend models/task.py
class Task(SQLModel, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="user.id", index=True)
    title: str = Field(max_length=200)
    description: Optional[str] = Field(default=None, sa_column=Column(Text))
    completed: bool = Field(default=False)
    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow)
```

**Migration Strategy**:
- Phase I: No migration needed (new project)
- Future migrations: Alembic with SQLModel support (alembic revision --autogenerate)
- Neon PostgreSQL supports zero-downtime migrations via branching
- Development: create tables on first run via SQLModel's `create_all` (dev only)

**Connection Management**:
- Single `DATABASE_URL` in `.env`: `postgresql://user:pass@host:port/dbname`
- Neon serverless connection string format: `postgresql://user:password@ep-xxx.region.aws.neon.tech/dbname?sslmode=require`
- Connection pooling handled by Neon (serverless)
- SQLModel engine created once at startup, session per request
- Handle connection errors gracefully with retry logic

## Security Considerations

**Authentication & Authorization**:
- Passwords: bcrypt with cost 12, never store plaintext
- JWT: HS256 algorithm, 7-day expiry, rotated secrets in production
- Token storage: HTTPOnly cookies prevent XSS attacks
- CSRF protection: Better Auth handles CSRF tokens for state-changing requests
- Session management: Stateless JWT means no server-side session storage
- Logout: Client clears cookie (no server invalidation needed with short expiry)

**Data Isolation**:
- Every database query includes `WHERE user_id = current_user.id`
- No endpoint returns data without user_id filter
- Get task by ID first checks ownership before returning
- Update/delete operations verify ownership before executing
- 404 for unauthorized access (not 403) to hide resource existence

**Input Validation**:
- All inputs validated via Pydantic/SQLModel field definitions
- Email format validation with regex
- Length limits: title 1-200 chars, description 0-1000 chars, email max 255
- SQL injection prevention via parameterized queries
- XSS prevention: frontend escapes all user-generated content, Content Security Policy headers
- Rate limiting: Consider implementing for auth endpoints (prevent brute force)

**Error Handling**:
- No stack traces or internal details exposed to clients
- Generic "Internal server error" for unexpected failures
- Descriptive messages for user errors (validation, not found, etc.)
- Log errors server-side with correlation IDs for debugging
- Timeout handling for database operations

**CORS & Deployment**:
- CORS: Allow frontend origin only (Vercel production URL, localhost:3000 for dev)
- Security headers: X-Frame-Options, X-Content-Type-Options, Content-Security-Policy
- HTTPS only in production (enforced by Vercel and Neon)
- Environment variables: DATABASE_URL, JWT_SECRET never committed to git
- Principle of least privilege: database user has minimal required permissions

## Error Handling Strategy

**Backend Errors**:
- ValidationError (Pydantic/SQLModel) → 400 Bad Request with field-specific messages
- HTTPException from dependencies → Status code and message as specified
- IntegrityError (SQLAlchemy) → 409 Conflict (duplicate email, FK violations)
- NoResultFound → 404 Not Found
- JWTError → 401 Unauthorized (invalid/expired token)
- OperationalError → 503 Service Unavailable (database connection issues)
- Generic Exception → 500 Internal Server Error (log and monitor)

**Frontend Errors**:
- Network errors: Offline/unreachable backend → "Connection error, please try again"
- HTTP error status: Display error message from response or fallback
- Validation errors: Display field-specific errors near inputs
- Auth errors: Redirect to login on 401, clear invalid token
- Unexpected errors: Generic message with option to retry
- Loading states: Disable buttons, show spinners during API calls

**Error Types by Endpoint**:
- Login: 401 for wrong credentials, 400 for invalid input
- Register: 409 for duplicate email, 400 for validation errors
- Tasks (GET): 401 for missing auth (redirect on frontend)
- Tasks (POST): 400 for validation, 401 for no auth
- Tasks (PUT/PATCH/DELETE): 404 for not found/not owned
- All endpoints: 500 for server errors (monitor:alert ratio)
